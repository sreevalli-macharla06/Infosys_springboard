## 1. Overview & Objective

Milestone 2 transitions the threat dashboard from static log aggregation ("*What happened?*") to an intelligent machine learning detection engine ("*Is this activity suspicious, and how suspicious is it?*").

This document serves as the **Data Contract** between backend data preprocessing, model training (`Isolation Forest` & `Random Forest`), and API prediction endpoints. It establishes the feature selection criteria, derived feature formulas, leakage safeguards, and preprocessing requirements based on empirical inspection of the Milestone 1 `security_events` dataset.

## 4. Identifier & Data Leakage Safeguards

To prevent overfitting, artificial accuracy, and target leakage, specific columns are explicitly excluded from model training ($X$).

### A. Direct Identifiers (Excluded)
- `event_id`: Unique primary key per document (`EVT000001` - `EVT010000`).
- `timestamp`: Raw ISO timestamp string. Converted into numeric `hour`, `is_weekend`, and `after_hours_flag`.
- `source_ip`: High-cardinality IP address (1,791 unique values). Memorization causes overfitting.
- `destination_ip`: High-cardinality IP address (1,297 unique values). Aggregated into `unique_destination_count`.
- `username`: Direct entity identifier. While only 6 unique users exist in the dataset, direct identifiers do not generalize to unseen users. Replaced entirely by behavioral aggregates (`events_per_user`, `unique_destination_count`).

### B. Target & Post-Event Leakage (Excluded)
- `event_type`: The **supervised target label** ($y$) for Random Forest classification. Must never be used as an input feature ($X$).
- `technique_id`, `technique_name`, `tactic`: Direct 1-to-1 deterministic mappings from `event_type` (e.g., `SQL Injection Attempt` $\rightarrow$ `T1190`). Including these would result in 100% trivial data leakage.
- `risk_level`, `login_risk`, `threat_confidence`: Synthetic post-event risk assessment fields generated by earlier rules or mock modules.

### C. Zero-Variance Columns (Excluded)
- `source_country`, `destination_country`, `year`, `month`: Contain a single constant value across the entire M1 dataset (`"India"`, `2025`, `8`). Zero variance offers no mathematical utility for Isolation Forest or Random Forest split criteria.

## 5. Derived Features & Inference Strategy

### 1. `impossible_travel_flag`
- **Concept:** Flags instances where a user logs in from two distinct source countries within an impossibly short physical travel time window.
- **Source Fields:** `username`, `timestamp`, `source_country`.
- **Derivation Algorithm:**
  1. Group events by `username` and sort chronologically by `timestamp`.
  2. Compute time delta $\Delta t$ between consecutive logins for the same `username`.
  3. Compare `source_country` of consecutive logins.
  4. If `source_country[t]` $\neq$ `source_country[t-1]` AND $\Delta t < \text{THRESHOLD_HOURS}$ (default = `4.0` hours), set `impossible_travel_flag = 1`, else `0`.
- **Configuration Note:** The 4.0-hour threshold is a documented project heuristic (`IMPOSSIBLE_TRAVEL_WINDOW_HOURS = 4.0`).
- **M1 Dataset Limitation:** In the baseline M1 `security_events.csv`, `source_country` equals `"India"` for 100% of records. Consequently, `impossible_travel_flag` evaluates to constant `0` during offline model training. **The trained ML models cannot learn a non-zero split decision on `impossible_travel_flag` from the baseline M1 CSV data alone.** However, the feature remains active for live API inference (`POST /predict`) when geo-diverse payloads are ingested AND serves as an explicit boost signal in the hybrid rule-based scoring engine (`services/scoring_service.py`).

### 2. `events_per_user` & `unique_destination_count` (User Behavior Aggregates)
- **Offline Training Strategy:** Computed using a strict causality constraint (`timestamp < T`). For any given event at time T, only strictly prior events from the same user contribute to the history. Same-timestamp events do not contaminate each other.
- **Live Inference Strategy (`POST /predict`):** When a single event is posted:
  1. The service queries historical events for that `username` from MongoDB `security_events`.
  2. The incoming event is combined with historical events up to its timestamp.
  3. Aggregate metrics (`events_per_user` and `unique_destination_count`) are calculated dynamically.
  4. Future events are strictly excluded to maintain temporal causality.

### 3. `after_hours_flag`
- **Source Fields:** `hour`.
- **Derivation Algorithm:** `1` if (`hour < 8` or `hour >= 18`), else `0`.
- **Output:** Binary (0/1).

## 6. Preprocessing, Encoders & Model Pipeline Contract

### A. Preprocessing & Encoding Pipeline (`ml/preprocessing.py`):
1. **Missing Value Imputation:** Impute missing `os` values with `'unknown'`.
2. **Feature Engineering:** Calculate `impossible_travel_flag`, `events_per_user`, `unique_destination_count`, and `after_hours_flag`.
3. **Categorical Encoding:** One-Hot Encode `protocol` using `sklearn.preprocessing.OneHotEncoder(handle_unknown='ignore', sparse_output=False)`.
4. **Tree-Based Scaling Strategy:** Both primary algorithms (**Isolation Forest** and **Random Forest**) are tree-based models invariant to monotonic feature scaling. Scaling (e.g. `StandardScaler`) is not mandatory for tree split optimization.
5. **Artifact Persistence:** The fitted preprocessing transformer/pipeline will be saved as `models/preprocessor.pkl` alongside trained model weights (`models/if_model.pkl` and `models/clf_model.pkl`).
6. **Inference Pipeline:** During `POST /predict`, `model_loader.py` loads `preprocessor.pkl` and transforms incoming event features. **A new scaler/encoder is NEVER independently fitted during live inference.**

## 8. Data Quality & Assumptions

1. **Static Data Integrity:** All M1 CSV files remain untouched and immutable.
2. **Reproducibility:** Random state seeds (`random_state=42`) will be strictly enforced across Isolation Forest and Random Forest algorithms.
3. **Model Decoupling:** FastAPI loads pre-trained `.pkl` artifacts at startup and never retrains models on incoming requests.
